# value-investing-analyst 历史回放验证与自我迭代

> 复用方式：把本文件全文投喂给 AI，或直接说「按 `backtest/PROMPT.md` 执行第一批」。
> 本文件是**测试资产**，与对外展示的 `cases/` 目录严格分开。

## 你的身份

你同时是两个角色：**拥有 40 年 A股/港股/美股实战经验的资深价值投资者**，以及**熟悉本 skill 全部脚本与阈值的专家开发工程师**。前者判断结论是否违反投资常识，后者把问题定位到具体文件与具体行。

你的目标**不是证明这个系统正确**，而是**制造一次真正的失败**——找到必须修改引擎才能修复的缺陷。一轮跑完全部通过时，默认结论是「案例选得太温和」，而非「系统已足够好」。

## 一、绝对纪律：信息截断

唯一不可妥协的红线。任何一次违反，该案例结果直接作废。

- 每个案例有 `information_cutoff` 日期。你**只能**使用该日期之前已公开披露的年报、季报、公告，以及该日收盘价。
- **禁止任何后见之明**：包括你脑内记忆中的后续走势、后续年度财务数据、"我们现在知道"类推理，以及任何暗示结局的措辞。
- 你**已经知道答案**。这是无法回避的污染源。因此必须：**先完整跑完分析并把结论落盘，再看答案比对**。禁止先看答案后写分析。
- 每份报告开头自陈「本报告仅使用 YYYY-MM-DD 及之前的公开信息」，结尾列出全部引用数据的 `publish_date`，晚于截断日的自行标红作废。
- 拉不到截断日之前的历史财报时，**如实报告「数据不可得」并跳过**，绝不用当前数据近似替代。这条比跑完案例重要。

- **文献时点 vs 事实时点**：允许用晚于截断日的文献**回取**截断日之前的客观事实（收盘价、
  已披露报表数字），但必须：① 在 `information_set` 标注「事实时点 X，载体文献 Y（晚于
  截断日）」；② 只取该文献中的**客观历史数字**，禁止使用其中的前瞻表述、管理层讨论、
  后续事件描述；③ 优先寻找截断日之前的原始载体，回取仅作兜底。
  （第一批柯达案实际用了 FY2012 10-K 的封面市值锚点回取 2011-06-30 收盘价——事实本身
  当日可知、不构成红线违反，但原协议未定义该边界。）

## 三、排期

不必一次做完。建议节奏如下，每批之间留出改引擎与全量回归的时间。

| 批次 | 主题 | 案例数 | 建议时点 | 前置条件 |
|---|---|---|---|---|
| 第一批 | 五类基础判别力 + 排雷对照 | 6 | 已完成 | 无 |
| 第二批 | 混合样本与结构性误判 | 6 | 已完成 | **硬前置**（见下） |
| **第四批** | **假阳性专项**（前两批在结构上无法暴露） | 6 | **第三顺位执行（2026-09-10 提前）**；**任何放松性改动之前必须先建立本批基线** | 假阳性轨 + FP/FN 双向统计已在 runner 实现（✅ 2026-09-10） |
| 第三批 | 行业专属口径与极端情绪 | 6 | 第四批基线建立后 | 第四批 FINDINGS 已出且假阳性基线写入 `assertion_baseline.json` |
| 第五批 | 类型卡阈值锚 + 豁免收窄验证 | 6 | 第三批完成后 | 第三批未遗留未定级的 observations |

**批次编号与执行顺序解耦（2026-09-10 裁决，REQ-P0-01）**：批次编号是案例设计时的标签，
保留不改（密封库 payload、BATCH2_FINDINGS 8.7 检验场、observations 触发映射均引用编号）；
**执行顺序是 1 → 2 → 4 → 3 → 5**。理由：第三批含 2 个假阴性专项案例（Meta / 伊利），
若其结果先于假阳性基线出现，会形成「再放松一点就能救回」的压力，而此时没有任何对照能证明
放松不会放进坏公司。刹车片必须先于油门。

**假阳性对照混入纪律（第三批起每批强制）**：每批案例表中须有 **≥1 个** `fp_control=true`
的假阳性对照案例（看起来该买、事后本金永久损失），从第五之二节末尾的替补池选取，答案不经
ANSWERS.md 明文中转直接密封。没有对照的批次，其「假阳性轨 0 例」只能表述为「未被检验」。

**第四批的特殊地位**：它不是"再加一批案例"，而是**放松性改动的前置条件**。第八节元问题 4 已
写明，第一批 6 案例中 4 个是明确的该拒/该排雷样本，假阳性在结构上不可能暴露。这意味着
`observations.md` 中 OBS-STAGE4-03 那一族放松性改动（R1 家族、基准增速、折现率下限对宽护城河
的适用性）**目前没有任何样本能验证它们是否破防**——现有防线（柯达/康美/海控/福耀）全是信号
明显的样本，防线强度被系统性高估。第四批的案例 19/20/23 就是这些改动的刹车片。
两批 12 案的 FP/FN 双向统计（runner 自动输出）已量化这一点：假阴性率 75%（3/4）、
假阳性率 0%（0/7）但对照案例数为 0——「系统性保守」目前只有一侧证据。

**第二批的硬前置（已全部就位，2026-09-06）**：

- [x] 答案已移出 PROMPT.md → `ANSWERS.md`（本文件可安全全文投喂）
- [x] 告警码注册表 `scripts/alert_codes.py` + 引擎输出稳定代号
- [x] 断言 runner `scripts/run_backtest_assertions.py`（断言 + 漂移 + 基线）
- [x] 6 个存量案例已回填 `answer.json` 与 `codes`，基线建立、0 回归
- [x] 第一批裁决的工程类改动已实施（量纲哨兵 / 快照三角校验 / 护城河一致性 / 触发器承接与可达性 / S2c 最差年 / S2e 折现率下限 / 有效门槛披露）

**软前置（明确不作为第二批前置）**：判别逻辑的放松性改动（原 R1 家族、基准增速、折现率下限对宽护城河的适用性）。理由：这些均只有茅台 1 例档位不匹配，未达第五节的 2 案例门槛；且第二批在「未放松」状态下跑，还能为它们提供对照基线。详见 `observations.md` 的 OBS-STAGE4-03。

## 五之二、第四批案例：假阳性专项

前三批测的主要是"该拒的有没有拒出来"和"该买的有没有错过"。这两类都**无法暴露错买**。
本批全部选择「回放时点看起来该买、事后证明是错的」样本——利润真实、护城河叙事成立、
估值指标不难看，但结局是本金永久损失。

| # | 标的 | 回放时点 | 专门测什么 |
|---|---|---|---|
| 19 | 通用电气 GE | 2016-12-31 | 蓝筹伪装：连续分红 + 工业互联网叙事，利润受 GE Capital 与养老金假设影响，会不会因「宽护城河 + 高股息」直接放行 |
| 20 | 中国石油 601857.SH | 2007-11-05 | 上市即巅峰：护城河**真实存在**，但价格透支数十年。测护城河为真时闸门一能否独立否决 |
| 21 | Valeant VRX | 2015-07-31 | 高质量假象：ROE 与增速极高、名基金重仓，利润靠并购 + 提价 + 特许药房。测 `add-back` 与商誉链路 |
| 22 | 分众传媒 002027.SZ | 2018-05-31 | 真护城河 + 真现金流 + 真高 ROE，但处盈利周期顶点且新进入者烧钱补贴。测周期顶在「轻资产高毛利」外衣下能否识别 |
| 23 | 福特 F | 2005-06-30 | 价值陷阱正面版：PE 极低、PB 破净、股息率 6%+、百年品牌。测「便宜」会不会被直接当成安全边际 |
| 24 | 新城控股 601155.SH | 2019-06-30 | 治理与关键人风险：财务全优、估值合理，风险无法从报表读出。测系统能否**诚实声明能力边界** |

**选型说明（为何是这 6 个）**

- **不用诺基亚**。理由与第一批案例 3 一致且更强：本批要找的是"系统会兴奋地说买"的样本，
  而诺基亚是"看起来就危险、实际也危险"，任何系统都能拒，加进来只会白拿一分——正是本批
  要消除的保守度红利。诺基亚唯一有意义的假阳性时点是 2007-10（份额巅峰、iPhone 初代仍被
  轻视），但该时点与案例 20 高度同质（巅峰期真护城河 + 价格透支），同一维度不需要两个
  样本，留待第五批。
- **案例 20 与案例 23 是一对反向样本**：前者是"好公司 + 荒谬价格"，后者是"烂公司 + 便宜价格"。
  两者都会被粗糙的估值指标放行，但放行的路径不同——20 走"护城河宽 → 门槛放松"，
  23 走"PE/PB 低 → 安全边际充足"。必须同时存在才能覆盖两条放行路径。
- **案例 21 与第二批案例 9（Netflix）成对**：一个经营现金流为负但业务健康，一个报表全优但
  不可持续。若系统对两者的 `add-back` 处理方向一致，说明它判的是会计科目而非商业实质。
- **案例 24 预期会产出一条「无法修」的观察**，这不是失败。新城 2019-07 之前报表全优，
  Phase 0 查不出任何东西；崩塌源于控制权与关键人事件，是纯粹的表外、非财务、不可预测风险。
  本案例的交付物允许是一条**能力边界声明**——例如在决策卡中强制标注「关键人 / 控制权集中度」
  为不可量化风险项，并要求正面档位时显式披露「本结论不覆盖治理突发风险」。
  skill 当前的缺陷是没有任何地方标注「我不知道什么」。

**执行顺序要求**：19、20、23 必须在任何**放松性改动**（见第三节软前置）实施之前跑完并写入
基线。否则那些改动的"未破防"结论没有证据支撑。**2026-09-10 起本批整体提前至第三批之前执行**
（见第三节排期表）。

## 六、执行流程（每案例严格照做）

**Step 1 — 建档冻结（不得含任何答案）**
在 `backtest/<ticker>_<replay_date>/` 下创建 `meta.json`，**只**登记：`ticker` / `company` / `replay_date` / `information_cutoff` / `batch` / `case_id` / `purpose` / `prior_expectation`（你在跑分析之前的先验档位与理由）/ `contamination_disclosure` / `information_set` / `frozen_at`。写入后不得修改，用于事后检验你有没有被答案带偏。

**建档后立即提交**：`git add <case>/meta.json <case>/data/ && git commit -m "meta(<case>): 建档冻结"`——该 commit 必须早于 verdict commit。第二批神华案 verdict commit 先于 data+meta 提交，导致 Step 1 冻结无 git 时序证据，只能靠 meta 自陈。

**禁止**写入 `expected_verdict` / `must_trigger` / `actual_*` 等任何答案字段——它们属于 `answer.json`（Step 4 才创建）。第一批的教训：第九节原格式把答案字段与先验混在一个「跑前冻结」的文件里，自相矛盾，执行者只能把答案字段全留空，结果 6 个案例的 `actual_*` 与 `outcome_note` 全是 `null`，断言库实质为空。

**Step 2 — 完整跑一遍 skill**
不走捷径、不简化、不跳 Phase。Phase 0 排雷 → 数据采集与双源核对 → 定量画像 → 五维定性 → 估值与安全边际 → 双闸门定档 → 三人独立评估 + 芒格红队。产出标准 HTML 报告并通过 `verify_report.py`。

两条机器化纪律（第四批起强制）：① Phase 0 必须跑 `python3 scripts/forensic_screen.py <financials> --as-of <回放时点> -o data/forensic.json`，`--as-of` 保证只用当日已发布年报（`publish_date` 驱动），其输出的 `P0_*` 码原样进 `verdict.json.codes` 并标 `engine_derived`——人工登记的排雷命中若脚本未命中，须在 `diff.md` 说明是字段缺失（`insufficient_data`）还是条款未算术化；② 闸门二按 `reverse_dcf.py` 的 `gate2.pass`（四项参与判定）落 `GATE2_*` 码，护城河反推门槛 `GATE2_1_IRR_FAIL` 是诊断码、不构成闸门二不过的理由。

**Step 2.5 — 隔离检查（REQ-P0-05，第四批起强制）**
verdict 落盘**前**运行 `python3 scripts/prepare_case.py --seal-check backtest/<case>/`。检查四项：① 工作区无答案明文（answer.json/answer_source.md/diff.md）；② 密封库对应答案未被揭示；③ git 时序正常（answer 相关文件首次 commit 不早于 verdict commit）；④ ANSWERS.md 第三/四/五批段落无该案例明文。任一命中 → verdict.json 打 `"contaminated": true`，从战绩表排除。

**Step 3 — 落盘存档结论 + 时序存证**
把以下内容写入 `verdict.json`：`final_verdict` 与 `verdict_ordinal`（档位序数）、闸门一/闸门二结果、`codes`（本次触发的全部告警代号，取自 `scripts/alert_codes.py` 注册表）、`codes_provenance`（区分 engine_derived 与 manually_recorded）、三情景每股价值、期望年化 IRR、`frozen_before_diff: true` 与 `frozen_at`。

**REQ-P0-08 规则版本钉死（第四批起强制）**：verdict.json 须含 `rules_snapshot`（运行 `python3 scripts/prepare_case.py --snapshot-rules` 获取），包括 `skill_commit`（git hash）与 `thresholds`（安全边际门槛、折现率、排雷阈值等关键参数）。无此字段的历史案例视为"规则未知版本"，用当前规则重跑时须在 diff.md 声明。

**落盘后、提交前先体检**：`python3 scripts/run_backtest_assertions.py --lint-verdict <case>/verdict.json`——校验 codes 全部在注册表内（第二批 Zoom 曾杜撰 2 个不存在的告警 ID）、`codes_provenance` 必填（缺失时漂移检测比对降级，第二批神华即缺）、必填字段与档位文案自洽。**体检通过才允许提交**。

**落盘后立即单独提交**：`git add <case>/verdict.json && git commit -m "verdict(<case>): 结论落盘，未读答案"`。git 历史即时序证据，机器可验、事后无法伪造——第一批只有 3/6 案例有自陈的 `frozen_before_diff` 字段，文件 mtime 又会被 git 检出覆盖，「先落盘再看答案」这条纪律没有任何可验证痕迹。**此步完成后才允许进入 Step 4。**

**Step 4 — 比对答案**
此时才允许打开 [`ANSWERS.md`](ANSWERS.md) 的**当前案例段**（禁止通读全文），据此创建 `answer.json`（格式见第九节）。然后跑 `python3 scripts/run_backtest_assertions.py --case <case>` 做机器判定，并填写 `diff.md` 逐项回答：档位序数是否落入 `expected_verdict_set`；`must_trigger` 是否出现在 `verdict.json` 的 `codes` 中；`must_not_trigger` 是否被误触发；若不匹配，根因是数据错、阈值错、逻辑错还是方法论错，**必须落到具体文件与稳定条款号**（如 `S2c`、`[P4-G2c]`；若根因在 `references/` 而非 `SKILL.md`，须指向真实定义处——第一批唯一的行级定位就把 `references/moat-framework.md:33` 的 25% 门槛错记成了 `SKILL.md:110`，而后者根本不含该数字）。

`answer.json` 与 `diff.md` 在**后续 commit** 中提交，与 Step 3 的 verdict 提交分开。

**Step 5 — 判定是否需要改引擎**
只有同一根因在 **≥2 个案例**中重现，才允许改代码。**门槛按「档位不匹配的案例数」计，不按「观察到该机制的案例数」计**——第一批的 R1 修法曾用两个**完全命中**的案例（苹果、柯达）凑够 2 案例门槛，实际只有茅台 1 例产生档位错误，事后验算证明该修法对任何案例都无效。单案例不匹配先记入 `observations.md` 观察，防止为拟合个案破坏通用性。

**改码门槛的三类例外（立法自第二批实践，防例外解释权自我扩张）**。批次裁决中援引例外必须**显式引用编号 E1/E2/E3**，不得援引「合理性」；未在此立法的例外一律无效：

- **E1 官方预声明的引擎缺陷**：`must_not_trigger` 类断言失败，且该缺陷在 `ANSWERS.md` 中**先于执行被官方预判**（如 Netflix 烧钱告警误触发是官方预设的测试点）——此类修复属「对齐官方预设的测试意图」，非拟合个案。允许**单案例**修复，验收硬条件 = **负样本零漂移**（受影响告警族在其余全部案例的 codes 逐字不变）。
- **E2 输入校验 / 披露哨兵类改动**：不改变档位判定的纯 WARN / 纯披露改动（量纲哨兵、股息口径哨兵、schema 校验、敏感性带披露）。门槛按**观察到该机制的案例数**计（≥2），不按档位不匹配数计——此类改动本就无档位影响可计（S9b 先例：茅台档位不匹配 + 双汇档位命中，按机制观察数 2 例达标）。
- **E3 工程卫生**：不改变任何判别行为的修补（错误提示结构化、两脚本检查对齐、文档补全、采集科目覆盖、rerun 参数补全），不适用门槛（第一批 R4 先例）。

**判别逻辑的放松性改动无任何例外**：严格 2 案例（按档位不匹配计）+ 第四批假阳性基线（第五之二节）+ 红灯规则（第九节）。「官方预声明」不得扩张用于档位轨——官方预期与系统输出在**档位**上冲突时，无论预判看起来多合理，都只能等第二例（Netflix 档位轨即如此处理，见 OBS-2016-12-01）。

改动前后必须跑：① `python3 tests/run_tests.py`；② `python3 scripts/run_backtest_assertions.py --rerun --baseline backtest/assertion_baseline.json`（断言 + 引擎代号漂移 + 基线比对，**只有「回归失败」才是红灯**，已登记的 `known_failures` 不阻塞）；③ 既有 `cases/` 目录的报告校验。判别逻辑改动尤其要确认**四个该拒绝的样本不破防**（柯达/康美/海控/福耀）。

**放松性改动的额外硬条件**：④ 假阳性轨新增数必须为 0，否则按第九节**红灯规则**直接回滚，
不得用「救回了 N 个假阴性」抵扣；⑤ 第四批案例 19/20/23 必须已在基线中——第一批那四个
该拒样本（柯达/康美/海控/福耀）信号都过于明显，用它们当防线会高估防线强度。

## 七、事后答案

**答案已移出本文件**，存于 [`backtest/ANSWERS.md`](ANSWERS.md)（按批次与案例分段）。

**Step 4 之前禁止打开。** Step 4 时只读当前案例那一段，不得通读全文——
读一个案例会污染同批其余案例。

移出原因：原先答案与任务书同在一个文件，而本文件的复用方式是「全文投喂给 AI」，
于是执行者要读案例清单就必然读到答案。第一批 6/6 案例因此全部结构性污染
（每份 meta.json 的 `contamination_disclosure` 都记录了这一点），
「制造一次真正的失败」这个目标无法被验证。

**第三批起的隔离协议（B 档为默认，2026-09-09 修订）**

历史教训：原协议写死「每个案例派独立 subagent」（A 档），但实测执行环境 subagent 支持不稳定——
第二批 6 案仅神华 1 案真做到，其余 5 案同一主上下文连跑，战绩证据强度被迫降级
（见 BATCH2_FINDINGS.md 战绩表）。隔离的**目的**是「答案不进入执行上下文」，subagent 只是
实现手段之一且不可依赖。**第三批起 B 档为默认协议**：

**B 档 — 双会话 + 文件闸门（默认，已落地）**
1. **答案密封**：未执行批次（第三/四批）的答案已由
   `python3 scripts/prepare_case.py --seal` 从 `ANSWERS.md` 抽出，以 base64 逐案例封装在
   `backtest/sealed_answers/<案例目录名>.enc`——工作区中**不存在明文答案**；
2. 会话一只获得 `meta.json` 与 ticker / 回放日 / 截断日，跑完 Step 1-3、单独提交
   `verdict.json`（先跑 `--lint-verdict` 体检）；
3. **结束会话**（上下文清空）；
4. 会话二运行 `python3 scripts/prepare_case.py --reveal backtest/<case>/`——脚本机器校验
   三道闸门（G1 verdict 存在 / G2 verdict 已提交且无未提交修改 / G3 未重复揭示）后才解码
   落地 `answer_source.md` 到案例目录，然后据此做 Step 4。
   上下文清空 + 文件闸门 + 揭示动作机器可验，三重保险。
   单会话环境下 G2 闸门仍然有效（reveal 拒绝执行就是机器证据），效果略降但不劣于旧 C 档。

**A 档 — subagent（可选增强，不作依赖）**
环境确有稳定子上下文时可用：执行上下文中从未出现答案，主上下文只做 Step 4 比对。
**不得宣称采用 A 档而不实际逐案分派**——第二批的教训正是口头宣称与实际执行脱节。

**C 档 — 单会话、无法分轮（最低配）**
执行者与判定者**角色分离**：人跑完 Step 1-3 后，由
`python3 scripts/run_backtest_assertions.py --case <case>` 做**纯机器判定**，
只输出「命中 / 未命中 + 代号 diff」，**不把答案原文交给 AI**。

**git 历史禁令（任何档位）**：第一/二批答案仍在 git 历史的 `ANSWERS.md` 明文中；
密封库的 `.enc` 文件本身也在历史里。Step 4 之前**禁止**用 `git log` / `git show` /
任何解码工具回取任何批次的答案——违反即该案例作废（等同打开 ANSWERS.md）。

**共同兜底（唯一可机器验证的时序证据）**：`verdict.json` 必须**单独 commit**，且该
commit 必须早于答案文件落地的 commit（B 档下即 `answer_source.md` 的出现，由
`--reveal` 的 G2 闸门机器保证）。**任何档位下，缺少这条提交顺序证据的案例，
其结论不得写入 REPORT.md / BATCH<N>_FINDINGS.md 作为战绩依据。**

成对案例（神华/鞍钢、Netflix/Valeant、中石油/福特）**禁止在同一会话内连续跑**——
否则第二个必然被第一个锚定，成对比对的判别力检验失效。

## 八、必须回答的四个元问题

每批跑完后在 `backtest/BATCH<N>_FINDINGS.md` 中回答（第一批为 `BATCH1_FINDINGS.md`）。**统计口径必须与第九节的三条计分轨一致，同一案例不得同时计入互斥的两个桶。**

**文档纪律**：该文件**只记结论**——战绩表、关键发现、已被推翻的结论清单、仍未解决项。
推导过程、逐条复算、审查往返一律移入 `backtest/archive/`。若某条结论事后被推翻，
必须在结论文件的「已被推翻」表中登记，并在归档件顶部加失效标记——被推翻的结论不得无标记示人。

1. **假阴性成本**：统计正向案例中被判「观察等价格」或更低而错过的比例。**假阴性率 ≥1/3 即视为保守度超标**（不再要求「全部错过」才触发——第一批正向案例只有 2 个，原判据要 2/2 全错才成立，几乎不可能触发），须给出具体到字段与阈值的放松方案。每批须保证 **≥3 个正向案例**，否则本项统计不具判别意义。
   错过成本按 `earnings_driven_return` 与 `multiple_driven_return` 拆分陈述，**只有盈利驱动部分计入系统错误**，倍数扩张部分单列为「未捕获的情绪溢价」。第一批实证：福耀错过的 +185.6% 主体是 PE 13.3→52 的倍数扩张，而 2019 年归母实际 −29.7%——事前算术是对的。
   **判断正确 + 触发器事后真的触发**的案例（如福耀 2020-03-23 于 16.36 触发、触发后 +297% 优于回放日买入）应计**正确拒绝**，不得计入错过。

2. **判别力而非保守度**：统计正确拒绝与错误拒绝的比例，后者不低于前者则系统价值接近于零。三分法：
   - **判断错误**：档位错，且事后价格从未回到系统要求的区间 → 计错误拒绝（茅台：触发价 166.93 五年未触及）
   - **判断正确 + 触发器有效**：档位说贵，价格事后确实回落到触发区间 → 计**正确拒绝**
   - **判断正确 + 触发器失效**：价格未回落但基本面也未恶化 → 单列「机会成本」，不计错误

3. **有没有制造出一次真正的失败**：若整批全过，明确写出「本批案例强度不足」，并提出下一批更锋利的候选。

4. **假阳性成本**：读取第九节**假阳性轨**的统计结果——「官方期望拒绝/观察，系统给出小仓位试探或核心买入」的案例数。若 ≥1，须定位是哪一道闸门放行、放行依据的证据强度是否真的达标。放松性改动实施后本项**必须为 0**，否则按第九节**红灯规则**回滚。
   **注意**：若本批案例结构中不存在「看起来该买、实际该拒」的样本，须明确写出「本批无法暴露假阳性」，**不得以本项为 0 作为系统无假阳性的证据**——第一批 6 案例中 4 个是明确的该拒/该排雷样本，假阳性在结构上不可能暴露，而 REPORT.md 曾据此宣称「0 反向错误」。**第四批即为此结构性缺口而设**：在第四批基线建立之前，本项的 0 一律只能表述为「未被检验」，不得表述为「无假阳性」。
   **FP/FN 双向报告（REQ-P0-01，第四批起每批必填）**：直接引用 runner 输出的 `[FP/FN 双向统计]` 段，分行陈述假阳性率（分母 = 官方期望 <3 的负向样本）、假阴性率（分母 = 官方期望 ≥3 的正向样本）、弃权率、假阳性对照红灯命中率。目标区间 **FP ≤10%、FN ≤40%**（`run_backtest_assertions.py` 的 `FP_RATE_TARGET` / `FN_RATE_TARGET`，调整须同步本节并登记动因）。两个比率**不得合并为单一数字**，也不得用一侧的改善解释另一侧的恶化。累计口径（全部已执行批次）与本批口径各报一次。

## 八之二、批次收官闭环（每批跑完后的标准流程，第三批起生效）

目标：每批回测的产出（问题与优化点）必须**反哺 skill**，且反哺有门槛、有验收、有回写——
不允许「记了就算改了」，也不允许问题散落在过程文档里丢失。

**文件职能（两份，正交——不设独立路线图文件）**：

| 文件 | 职能 | 性质 |
|---|---|---|
| `observations.md` | **未决项台账（事实源）**：每个问题/优化点一条 OBS（根因 / 案例锚 / 候选修法 / 触发条件 / 状态）。跨批次追踪只看这里，状态变更必须回写 | 活文档 |
| `BATCH<N>_FINDINGS.md` | **批次结论档案**：战绩（三轨 + 证据强度 + 隔离降级）+ 四个元问题 + 跨案例裁决 + 已被推翻的结论 + 移交清单 | 定稿后不可变 |

历史教训：曾以独立的 `SKILL-UPGRADE.md` 作改造路线图，与 observations.md 的条目状态
形成两处事实源，状态漂移后只能互相追认（2026-09-10 已删除并入 `BATCH2_FINDINGS.md`
第八节作路线图快照）。**此后路线图不是文件，是 observations.md 中全部未关闭 OBS 条目的
集合**；每批 findings 只留一份移交清单（OBS id + 检验场案例），不复制台账内容。

**闭环六步**（全部完成该批才算收官）：

1. **登记**：各案 `diff.md` 的问题逐条登记进 `observations.md`（单案例不得直接改判别
   逻辑——第五节门槛）。登记时必须写明触发条件（第二例的形态定义）。
2. **收官**：写 `BATCH<N>_FINDINGS.md`——战绩表（三轨计分 + 污染降级）、四个元问题、
   跨案例裁决、已被推翻的结论清单。
3. **裁决**：对每个 OBS 定处置，三选一并记录理由——立即实施（披露级/校验级/E3 工程卫生）/
   等门槛（≥2 案例，写明检验场）/ 裁定不修（写明理由，防无据翻案）。
4. **实施与验收**：门槛达标项落码。验收三件套：`tests/run_tests.py` 全绿 +
   `--rerun --baseline` 无未登记回归 + 受影响告警族负样本零漂移；放松性改动另加
   假阳性轨零新增（红灯规则）。
5. **回写**：实施完成后回写 observations.md 条目状态（附验收证据）；findings 已定稿
   不再改，由下批 findings 的「上批移交项处理结果」承接。
6. **移交**：未决项写入本批 findings 的移交清单（OBS id + 检验场案例）。下批启动前
   先读上批移交清单，逐项处理。

**继承纪律**：`BATCH<N+1>_FINDINGS.md` 必须以「上批移交项处理结果」开篇——每个移交
OBS 在本批是**复现了**（达门槛，进入第 4 步）、**阴性对照了**（降频或关闭）、还是
**继续等待**（检验场更新到第 N+2 批）。三者必居其一，不允许静默遗漏。

## 九、案例登记文件格式

**两个文件，创建时点严格分离。** 第一批的教训：原格式把答案字段（`expected_verdict` / `actual_*` / `outcome_note`）与「跑前冻结的先验」混在同一个 `meta.json` 里，而 Step 1 要求跑分析前冻结——自相矛盾。执行者只能把答案字段全留空，于是 6 个案例的 `actual_*` 与 `outcome_note` 全是 `null`，第九节承诺的「可自动判定的断言」实质为空。

### `meta.json`（Step 1 跑前冻结，**不含任何答案**）

```json
  },
```

### `answer.json`（Step 4 才创建，**全部是答案**）

```json
  "expected_verdict_set": [3, 4],
  "expected_gate1": true,
  "expected_gate2": true,
  "must_trigger": ["CYCLE_PEAK"],
  "must_trigger_any": [["NOT_CONVERGING_FLOOR_LOW", "PEAK_DRAWDOWN_STAGNANT"]],
  "must_not_trigger": ["VALUE_TRAP"],
  "known_failures": [],
  "fp_control": false,
  "actual_3y_total_return": 0.42,
  "actual_5y_total_return": 1.15,
  "earnings_driven_return": 0.60,
  "multiple_driven_return": 0.55,
  "actual_max_drawdown": -0.32,
  "outcome_note": "低成本煤+一体化运输，真周期底部",
  "answer_source": "ANSWERS.md 第二批 + 行情复核来源"

```

### 档位序数

`排除=0 / 拒绝=1 / 观察等价格=2 / 小仓位试探=3 / 核心买入=4`（定义见 `scripts/alert_codes.py` 的 `VERDICT_ORDINAL`）。官方不约束档位时 `expected_verdict_set: null` → 档位轨不计分，但**错过成本仍进入元问题 1 的统计**。

### `fp_control` 字段（REQ-P0-01）

标记该案例是**假阳性对照**（第四批全部 6 案 + 第三批起每批混入的 ≥1 例）。runner 据此
统计「假阳性对照红灯命中率」= `must_trigger` 全部命中且未产生假阳性的对照案例占比——
即刹车片有没有踩下。普通负向样本（如柯达/康美，信号明显的该拒样本）**不标** `fp_control`，
否则会用容易的样本稀释对照难度。runner 同时按 `expected_verdict_set` 自动给每个案例贴
样本角色：`negative`（期望最高 <3）/ `positive`（期望最低 ≥3）/ `mixed`（跨 3）/
`unscored`，FP 率与 FN 率的分母分别是 negative 与 positive 的案例数。

### 断言 ID 铁律

`must_trigger` / `must_trigger_any` / `must_not_trigger` 只能取自 `scripts/alert_codes.py` 的 `ASSERTIONS` 注册表，**自然语言断言不被接受**。第一批出现过 5 种命名风格并存（`S8_value_trap` / `cash_interest_contradiction` / `not_converging_floor_low` / `gate1_wide_moat_25pct` / 中文「周期高位」），导致 17 条观察全部只能人工解读。

注册表同时定义**等价关系**：一个断言映射到**一组**代号，任一命中即满足。这不是放水——海控案官方要求断言「周期高位」，而引擎实际输出 `NORM_BASE_UNUSABLE`（全期均值为负、均值路径数学失效，引擎拒绝给标签，比硬给错标签更严格）。该等价现已显式写入 `ASSERTIONS["CYCLE_PEAK"]` 并被测试锁定，不再靠人工「两层合读」裁定。

反向同样重要：**观察级、非造假形态的代号绝不能进造假类断言组**（如 IFRS16 准则切换、分红幻觉），否则「负样本零误杀」这类断言会产生假阳性。

### 三条独立计分轨（不得互相抵扣、不得合并为单一「命中」）

- **告警轨**：`must_trigger` 命中数 / 漏判数 / `must_not_trigger` 误触发数
- **档位轨**：`verdict_ordinal` 是否落入 `expected_verdict_set`
- **假阳性轨**：仅统计「官方期望拒绝 / 观察，系统却给出正面档位（序数 ≥3）」的案例

第一批曾把福耀同时计入「命中」（总览表）与「错误拒绝」（元问题 2）两个互斥的桶，头条战绩
因此偏乐观。分轨计分是对该问题的结构性修正。

**为什么假阳性必须单独成轨**

设想一个假系统，逻辑只有一行：无论输入什么公司，一律输出「观察等价格」。把前三批 18 个
案例喂给它——该拒的（柯达、康美、海控、中石油）它全对；该买的（茅台、苹果、福耀、Meta）
它全错，但这些只计「错过」。跑完一算，它能拿到十几个"正确拒绝"，战绩表相当漂亮。

这就是现有战绩的结构性风险：**它很可能来自保守度，而非判别力**。前三批 18 例中，系统正面
看多且事后正确的只有苹果 1 例，而该案自陈「近乎重跑」、证据强度还要降级。也就是说，
整套体系"敢买且买对"的能力至今几乎未被验证。

假阳性轨的关键性质：上述假系统在这条轨上**永远是零分、也永远不失分**（它从不给正面档位）。
于是该轨的分数成为一个纯信号——**系统是否具备在正确的时候敢于出手、且出手不打脸的能力**。

**为什么不能合并进总分：代价不对称**

错买与错过的代价量级不同。错过福耀，损失是没赚到的 +185.6%，本金一分未少，机会还会再来。
错买中石油 2007（48 元买入、最低 7 元），本金蒸发约 85% 且不可逆——一笔就能抹掉一个组合
十年的复利。真实亏损从不来自错过，而来自"我算过、我确信、我买了"。

若混入单一总分，会出现荒谬结论：某改动"救回 2 个错过、新增 2 个错买"，总战绩不变甚至更好，
而系统实际已显著变危险。这不是假设——`observations.md` 中 OBS-STAGE4-03 正在考虑的放宽闸门
以救茅台，风险恰在此处。

**权重纪律**：假阳性一例的严重性显著高于假阴性一例。禁止用"救回 N 个假阴性"抵扣
"新增 1 个假阳性"。两者在 REPORT.md 中必须分行陈述，不得给出合并后的单一战绩数字。

### 红灯规则（放松性改动的硬否决）

**任何判别逻辑的放松性改动，只要使假阳性轨新增 ≥1 例，即直接红灯否决**，不论它救回了
几个假阴性、不论总战绩是否改善、不论三人评分与红队是否支持。

- 判定方式：改动前后各跑一次 `--rerun --baseline`，比较假阳性轨案例集合。
- 例外流程：无自动例外。若确信该假阳性属答案争议（官方期望本身可辩），须先在
  `observations.md` 立案、修正 `answer.json` 并说明依据，改动本身仍须回滚等待重跑。
- 假阳性轨不接受 `known_failures` 登记豁免。其余两轨的已知失败可登记不阻塞，
  假阳性一旦出现即为红灯——这是与另两轨的**不对称设计**，是刻意的。

### `known_failures`

登记**已知且已记录在案**的失败类型（`verdict_track` / `must_trigger` / `must_not_trigger` / `engine_drift`）。只有未登记的失败才算回归——否则门禁永远是红的、无法当回归闸使用。若某项登记的失败已消失，runner 会提示「登记过期」要求移除，防止拿旧登记掩盖新问题。

### 一键重跑

```bash
python3 scripts/run_backtest_assertions.py --batch 2            # 断言判定
python3 scripts/run_backtest_assertions.py --rerun              # 附带引擎代号漂移检测
python3 scripts/run_backtest_assertions.py --rerun --baseline backtest/assertion_baseline.json
```

每次改引擎后必须重跑并对比基线。**无法一键重跑的批次，其战绩统计不得写入 REPORT.md 作为结论依据。**
