## 答案置信度与修订流程（REQ-P2-01）

**为什么**：`answer.json` 的标签被当作真值使用，但有噪声的标签会把系统训偏——
如果一个案例的「正确答案」本身是错的，系统为了命中它做的每一次规则调整都在朝
错误方向走。海控（周期顶部纪律 vs 事后回报）与 Netflix（标签依赖「框架应有
成长股通道」）即此类。低置信度案例单列后，规则调整只对高/中置信度案例负责。

### 一、置信度规则表（赋值必须引用条目编号）

| 条目 | 判据 | 等级 |
|---|---|---|
| H1 | 事后事实已验证（数值口径齐且有 price_basis 留痕，或不可辩驳事实：破产/违约/造假坐实）且支撑期望区间内全部档位的**共同语义** | 高 |
| H2 | 「不排雷 / 不误触发」类负对照约束，事后无任何反例暴露 | 高 |
| M1 | 事后证据**双向**：期望区间两端各有实证（一端兑现、另一端反向），档位取舍依赖价值判断 | 中 |
| M2 | 事后验证为**定性**：无数值锚与口径声明 | 中 |
| M3 | 单档答案但**边际贴近门槛 / 窗口敏感**：换评估窗口或门槛值方向即变 | 中 |
| L1 | 官方已登记争议（需求正文或 observations 点名） | 低 |
| L2 | 标签依赖**规范性主张**：「正确档位」以框架应当有某通道/某能力为前提，通道能力与标签间存在未消解落差 | 低 |
| L3 | 纪律裁决与事后结果方向冲突且**未在答案内消解**（如无数值锚无法复核） | 低 |

落地为 `answer.json` 两个字段：`confidence`（`high` / `medium` / `low`）与
`confidence_basis`（引用上表条目编号 + 事实依据）。**缺失 confidence 按高置信度
计分**——统计完整性优先，不允许靠漏填字段把 inconvenient 的案例静默丢出分母；
要排除主指标必须显式标 `low` 并给出依据。`acceptable_grades`（需求原文的另一
字段名）不设独立取值——`expected_verdict_set` 即「可接受档位区间」，镜像字段
若出现必须与之完全一致（runner lint 强制，双声明分叉即失败）。

**计分语义**（runner 已实现）：`low` 案例三轨仍完整评测、仍进基线代号比对
（引擎回归防护与答案质量无关），但**不进** FP/FN 分母、战绩计数与回归门禁，
在 `[低置信度答案]` 段单独列示；其假阳性**仍触发基线红灯**——「不错买优先」
不容静默消失，争议标签的例外路径只有下面的修订流程。

### 二、赋值时点纪律（反博弈核心）

低置信度案例不进主指标，意味着「谁在何时赋值」决定这条机制会不会被用来洗掉
难看的假阴性。因此：

1. **密封批次（第三批起）：预注**——置信度须在**该案例 verdict 存在之前**落进
   密封 payload（`prepare_case.py --annotate-confidence <case> --confidence <x>
   --basis "<条目依据>"`），与 REQ-P2-09「靶在箭前」同构。已预注的置信度随
   `--reveal` 一并揭示，揭示会话不得改动。
2. **未预注的密封案**：揭示时按规则表赋值，`confidence_basis` 须以「揭示时赋值」
   开头并引用条目编号（此时 verdict 已知，赋值须特别克制——只有 L1 类官方
   点名争议才允许标 low）。
3. **已揭示案例**：改置信度 = 答案修订，只能走下面的五步流程；
   `--annotate-confidence` 对已揭示案例拒绝执行。
4. 存量 18 案密封库已于 2026-09-14 全量预注（high 12 / medium 6 / low 0，
   各案依据存于 payload 内）——该时点早于第三/四/五批任何 verdict，属合法预注。

### 三、修订流程（五步，缺一不可）

> 适用对象：`expected_verdict_set` / `must_trigger` / `must_not_trigger` /
> `confidence` 的任何事后改动。密封案例的答案修订 = 修订 payload 后重新密封
> （`--annotate-confidence` 仅限置信度；档位/断言修订直接改 payload 并在
> `confidence_history` 同款留痕字段登记）。

1. **提出**：在 `observations.md` 立案（OBS 条目），写明案例、拟改动、动因。
   触发源通常是：档位轨长期未命中且根因定位到答案本身、低置信度案例在
   `[低置信度答案]` 段反复出现、或新证据（行情复核/年报更正）与标签冲突。
2. **举证**：举证必须落在**答案内在属性**上（引用规则表条目 + 事后数据口径
   或纪律条款号），不得以「系统没命中」作为改答案的理由——那是拟合，不是修订。
   涉及档位改动的，须同时回答「改动是否使该案更容易命中」；若答案是 yes，
   额外说明为何不是拟合（如：新行情复核推翻了旧数值）。
3. **复核**：第二人（或隔日的新会话）独立重推一遍：拟改动是否与
   「不错买优先」「峰值利润不作基期」等原则冲突。放松方向的修订（提高档位、
   删 must_trigger）一律加严复核。
4. **生效**：改 `answer.json`（密封案改 payload 重封），OBS 条目回写修订记录
   （日期、改动前后、举证链、复核人）。
5. **旧战绩重算**：`python3 scripts/run_backtest_assertions.py --case <case>`
   重跑；若改动影响 FP/FN 集合，`--baseline` 重写基线 `_fp_fn` 段（旧基线归档
   至 `archive/`）。已定稿的 `BATCH<N>_FINDINGS.md` 不回改——受影响结论由
   **下一批** findings 的「上批移交项处理结果」承接并标注「案 N 的答案已于
   YYYY-MM-DD 修订，原战绩口径见归档基线」。

### 四、与红灯规则的接口

放松性改动使假阳性轨新增 ≥1 例即直接红灯否决（PROMPT 第九节）——**低置信度
答案的案例不豁免此规则**：其假阳性同样触发 `--baseline` 的 `new_fp` 红灯，
只是输出会标注「低置信度答案，例外路径 = ANSWERS.md 修订流程」。流程是：
改动先回滚 → 立案修订答案 → 修订生效后重跑 → 若假阳性消失且第四批刹车片
不破防，改动方可重新提交。禁止用「标个 low」代替回滚。
