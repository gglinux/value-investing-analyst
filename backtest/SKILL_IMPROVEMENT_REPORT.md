### 1.2 发现的执行缺陷（6 项）

#### E1｜断言库实际为空——这是最严重的一项

`PROMPT.md` 第九节原话："`must_trigger` 与 `must_not_trigger` 是整套回放的核心——它们把「系统当时该不该报警」变成**可自动判定的断言**，而不靠人事后解读。"

实测结果是：**全部 6 个案例的断言都只能靠人事后解读。**四层证据：

1. **schema 分裂**：福耀（600660）与海控（601919）的 `meta.json` 完全偏离第九节格式，缺 9 个必需字段——`replay_date`、`information_cutoff`、`batch`、`expected_verdict`、`expected_gate1/2`、`must_trigger`、`must_not_trigger`、`frozen_at` 全无，改用 `analysis_date`/`price_date`。两案的断言被塞进 `prior_expectation` 内部，且是自然语言（海控：`["周期高位","强制禁用当期基期"]`；福耀：一整句"全部造假类告警（康美案清单全集）：货币资金异常/存贷双高/……"）。
2. **断言 ID 5 种命名风格并存**，无注册表：`S8_value_trap`（茅台）/ `cash_interest_contradiction`+`ocf_profit_divergence`（康美）/ `not_converging_floor_low`+`peak_drawdown_stagnant`+`phase0_false_fire`（柯达）/ `gate1_wide_moat_25pct`+`gate2_all_three`（苹果）/ 中文短语（海控、福耀）。
3. **答案键全空**：6 个案例的 `actual_3y_total_return` / `actual_5y_total_return` / `actual_max_drawdown` / `outcome_note` **全部为 `null` 或字段不存在**。`REPORT.md` 引用的 9.06x、5.61x、+185.6%、−87.7%、−81.9% 全部只存在于 `diff.md` 的散文与表格里（推导过程有、可复核），**没有任何结构化落盘**。
4. **引擎侧根本没有可匹配的标识**：`check_scenarios.py:608-610` 的告警输出是 `print(f"  [WARN] {w}")` / `print(f"  [FAIL] {e}")`——**自由文本字符串，无稳定 code/id**。`compute_metrics.py` / `reverse_dcf.py` 同样只有 `alerts`/`warnings` 文本数组。

**这第 4 点是 `REPORT.md` 完全没有识别到的根本缺口**：即使把 meta.json schema 全部统一、断言 ID 全部规范化，也依然无法自动判定——因为断言要匹配的对象（引擎告警）本身没有机器可识别的身份。**断言自动化的前置条件不在测试侧，在引擎侧。**

#### E2｜Step 3 → Step 4 的时序无防篡改证据

`PROMPT.md` 第六节 Step 3 明确："**此步完成后才允许进入 Step 4。**"

- 仅 **3/6** 案例的 `verdict.json` 含 `frozen_before_diff` 字段（茅台、苹果、柯达）；康美、福耀、海控**无任何时序证明字段**（福耀/海控连 `frozen_at` 都没有）。
- 文件 mtime 不可用作证据——全部显示 `09-05 17:09`（git 检出时间戳覆盖了原始 mtime）。
- 6 案例在 git 中由**同一个 commit**（`6c58fc4`）一次性提交，提交历史也无法还原 Step 3/Step 4 的先后。

结论：**"先落盘再看答案"这条纪律在 3 个案例上完全依赖执行者自陈，无任何可验证痕迹。**这不是指控——分析质量本身没露出被答案倒推的迹象——但协议层没有留下证据能力。

#### E3｜根因定位未达 Step 4 要求，且唯一的行级定位是错的

Step 4 要求根因"必须落到**具体文件与具体行**"。

- **5/6** 案例的 `diff.md` 无任何 `文件:行` 级定位；康美/福耀/海控/苹果/柯达连引擎文件名都没提（仅茅台提了 `SKILL.md` 与 `references/valuation-guide.md`）。
  - 部分可辩护：苹果/柯达/康美是完全命中案例，无不匹配项需要定位。但福耀与海控都在 observations 里提出了修法，理应落到文件行。
- **唯一的行级定位有一半是错的**：茅台 `diff.md:36` 写 "`SKILL.md:110`（闸门一：MoS ≥25%）"。实测 `SKILL.md:110` 是"5.5 三情景门禁"，**SKILL.md 全文根本不含 25% 这个门槛**——闸门一的 25%/40% 真实定义在 `references/moat-framework.md:33`。（同句的 `SKILL.md:111` 指向闸门二③，这个是对的。）

这暴露了一个通用问题：**SKILL.md 已有 14 次提交历史、当前 163 行，行号必然漂移**。用行号做根因锚点，写下的那一刻就开始腐烂。

#### E4｜publish_date 附录只有一半案例合规

`PROMPT.md` 第一节要求"结尾列出**全部**引用数据的 `publish_date`，晚于截断日的自行标红作废"。

- 结构化附录（标题即"附录（全部 publish_date）"）：**3/6**——茅台、苹果、柯达。
- 康美、福耀、海控：附录存在但无 `publish_date` 结构化清单（康美在正文散记了披露日，如"2016 年报（publish 2017-04-20）… 2017 年报（publish 2018-04-26）晚于截断日剔除"，实质合规但不可机器校验）。

#### E5｜战绩统计口径不一致，头条数字偏乐观

福耀案在 `REPORT.md` 内部被**同时计入两个互斥的桶**：

- 批次总览表：`✅ 排雷侧完全命中`；战绩口径："2 命中可接受集或官方不约束档位（海控/福耀）"。
- 元问题 2：`错误拒绝 = 茅台 + 福耀档位侧 = 2`。

于是头条"**5 命中 + 1 纪律性错过**"与元问题 2 的"错误/正确 = 2/3"来自同一批案例的两套口径。报告自己披露了这个拆分（"排雷侧/档位侧"），不算隐瞒，但头条口径客观上淡化了保守度成本。**根因是 PROMPT 没有把"排雷轨"与"档位轨"定义为两条独立计分线**（详见 PROMPT 审查 P5）。

#### E6｜污染程度存在案例间差异，苹果案接近无效样本

6 案例全部披露"已读 PROMPT 第七节答案"（结构性污染，PROMPT 自己承认不可避免）。但有两案更重：

- **苹果案**：`contamination_disclosure` 自陈"执行者在更早的 2016-05-13 自选回放任务中已对**同一公司、几乎同一时点**做过完整分析并得出「核心买入」结论——**本回放对其而言近乎重跑**"，且全部估值参数"沿用 2016-05-13 版"。
  → 苹果案是"全批唯一正面档位"，是 `REPORT.md` 元问题 2 论证"系统不是靠一律拒绝拿分"的**第一反证**。这个反证建立在一个近乎重跑的样本上，证据强度应当降级，而 `REPORT.md` 引用它时未降级。
- **柯达案**：三重污染，其中包括"行情锚定过程中暴露于 FY2012 10-K 披露文本"——**用截断日（2011-06-30）之后的文献去取截断日当天的事实（收盘价 3.58）**。事实本身当日可知，不构成红线违反；但 PROMPT 未定义"文献时点"与"事实时点"的区分规则（详见 PROMPT 审查 P12）。

### 2.2 不成立 / 需要修正的部分

#### C1｜R1 的验收标准无法执行（关键）

`REPORT.md` 第五节给 R1 定的验收标准是：

> "用茅台/苹果截断日数据重算回验；柯达/康美/海控/福耀四案 **verdict 与 must 断言不变**；`cases/` 全量回归通过"

结合 E1：**must 断言不存在机器判定能力，"断言不变"无法验证；`cases/` 也没有回归 runner。**第五节自己的勾选框也确认了这一点（"改动 #1-#4 实施并通过全量回归"仍未勾选）。

R1 改的是**情景概率与闸门阈值**——整个系统里最危险的参数（`REPORT.md` 自己说它是"双刃剑"）。在没有回归能力的情况下实施 R1，等于在没有测试的情况下改核心风控参数。

**→ 修正建议：R1 的实施顺序必须后移到断言基础设施之后。P0 不是 R1，是断言基础设施。**

#### C2｜第五节漏了一项前置改动：告警结构化 ID

R1-R5 五项改动里，没有一项解决 E1 第 4 点（引擎告警无稳定 ID）。而 R1/R2/R3 的验收**全部依赖**它：
- R1 要验"must 断言不变" → 需要断言可判定
- R2 要验"两例历史错位样本能告警" → 需要告警可识别
- R3 要验"决策卡含触发器字段" → 需要报告结构可校验

**→ 这是 REPORT.md 的一个实质遗漏，应补为改动 #0。**

#### C3｜"0 反向错误"的表述过强

`REPORT.md` 称"**反向错误 0**（无漏排雷、无错误排雷、无买入踩雷、无周期顶误判）"。这个结论在第一批成立，但**第一批的案例结构决定了它几乎不可能不成立**：6 案例里 4 个是"该拒绝/该排雷"，2 个是"该买入"。假阳性（该拒没拒）只有在"看起来该买、实际该拒"的样本上才会暴露，而第一批**没有这样的样本**（海控是明确的周期顶，柯达是明确的衰退末期）。

所以"0 反向错误"更准确的表述是：**本批未设置能暴露假阳性的样本**。`REPORT.md` 第六节第 4 点自己意识到了这件事（"第二批报告加入假阳性计数"），但第一节的战绩陈述没有加这个限定。

#### C4｜福耀"错过 +185.6%"的成本归因，REPORT.md 提了问题但没给口径

第六节第 5 点自问："倍数扩张不可预期，错过成本是否应全额计给系统？"——问题提得对，但没有给出裁决。这个口径直接影响元问题 2 的分母（错误拒绝到底算 1 例还是 0.5 例）。**建议在第二批前定死口径**（见第三节 P2-3）。

## 三、Skill 完善点清单（第 3 问）

按"是否阻塞第二批"分级。**P0 必须在第二批启动前完成，否则第二批产出的是又一批无法机器复核的观察。**

### P0-1｜引擎告警与闸门输出结构化 ID（新增，REPORT.md 未识别）

**问题**：`check_scenarios.py:608-610` 等处告警为自由文本 `[WARN] {w}`，无稳定标识；断言无法机器匹配。

**修法**：
1. 建立告警码注册表 `references/alert-registry.md`，每条告警分配稳定 ID，命名规范 `<层>_<语义>`，例如：
   - Phase 0 排雷：`P0_CASH_INTEREST_CONTRADICTION`、`P0_OCF_PROFIT_DIVERGENCE`、`P0_DEPOSIT_LOAN_DOUBLE_HIGH`
   - 三情景门禁：`S4_DISPERSION`、`S8_VALUE_TRAP`、`S_DIV_YIELD_DIMENSION`
   - 正常化：`NORM_CYCLE_PEAK`、`NORM_BASE_OE_FORBIDDEN`
   - 闸门：`GATE1_MOS_FAIL`、`GATE2_1_IRR_FAIL`、`GATE2_2_FLOOR_FAIL`、`GATE2_3_BEAR_IRR_FAIL`
2. 所有脚本的告警输出改为结构化对象：`{"id": "...", "level": "WARN|FAIL", "msg": "...", "evidence": {...}}`，保留人类可读文本，新增机器可读 ID。
3. `verdict.json` schema 固定 `alerts_triggered: [<id>...]`，断言直接对 ID 集合做包含/排除判定。

**验收**：6 个存量案例的 `verdict.json` 回填 ID 后，17 条观察对应的断言全部可机器判定。

**成本**：中等（约 10 处告警点 + schema 变更），但这是 R1/R2/R3 的共同前置，不做则后续全部无法验收。

### P0-2｜回放断言 runner（新增，PROMPT 承诺但工具不存在）

**问题**：`scripts/` 下无任何回放断言重跑工具；`PROMPT.md` 第九节承诺的"一键重跑全部断言"无实现。

**修法**：新增 `scripts/run_backtest_assertions.py`：
- 遍历 `backtest/*/`，读 `answer.json`（断言源，见 PROMPT 审查 P2）+ `verdict.json`（系统输出）
- 判定四项：档位是否落入 `expected_verdict_set`、`must_trigger` 是否全部出现在 `alerts_triggered`、`must_not_trigger` 是否全部未出现、闸门结果是否匹配
- 输出汇总表 + 非零退出码；支持 `--case` 单案例、`--batch N` 按批次
- 同时纳入 `cases/` 目录的既有案例（回归面）

**验收**：`python3 scripts/run_backtest_assertions.py --batch 1` 一条命令复现 REPORT.md 总览表。

### P0-3｜meta.json / answer.json schema 统一 + 校验脚本

### P1-3｜护城河评级自造词治理（新增，第一批未暴露但第二批会撞上）

**问题**：`references/moat-framework.md:35` 自陈——归档 11 案例中**只有 4 例用了标准词**（宽/窄/无），5 例用自造词（"中强"/"中级"/"极强"/"强"），2 例（谷歌、平安）"报告里根本找不到明确评级"。而该文件第 33 行明确："**两道闸门的门槛直接挂在这个词上**"（宽 ≥25% / 窄 ≥40%；IRR 门槛 16.5% / 21.8%）。

**为什么现在必须修**：第一批 6 案例的护城河评级都很明确，所以这个缺口没暴露。但第二批的鞍钢（无成本护城河）、双汇（传导型）、软银（非经营资产主导）**正是评级最容易含糊的类型**，而 R1 的"宽护城河定向放宽"又把更多权重压在这个词上——不治理就会出现"靠把窄写成宽来过闸门"的路径。

**修法**：`check_scenarios.py` 或新增门禁校验 `moat_rating ∈ {wide, narrow, none}`，非标准词直接 FAIL；报告模板强制该字段。
