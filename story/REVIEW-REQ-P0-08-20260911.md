## 2. 【P0】验收条款「按记录的版本重跑并复现原档位」在存量案例上不成立

### 2.1 存量案例根本没有「其记录的版本」

runner 汇总实测：`[规则版本] unknown: 12 例`。12 案全部无 `rules_snapshot`，需求写的验收主语（「其记录的版本」）在第四批之前不存在。需求文档自己把这项留成待办，但**验收条款没有降级路径**，读起来是一条已生效的硬标准。

### 2.2 实测重跑未复现

```
$ python3 scripts/run_backtest_assertions.py --as-of 1cc92c11 --case ZM_2021-10-31
   （1cc92c11 = ZM verdict.json 首次提交，即该案当时唯一的「版本」）
   → 引擎代号漂移：新增 [] / 消失 ['GATE2_1_IRR_FAIL', 'GATE2_2_FLOOR_FAIL',
     'GATE2_3_BEAR_FAIL', 'GATE2_FAIL', 'M_UNIT_SUSPECT']     ← 零复现
```

### 2.3 根因：`--as-of` 只钉规则、不钉数据

`run_backtest_assertions.py:273-278` 把自己 worktree 的 `backtest/` 删掉、软链到**当前工作区**的 `backtest/`，注释写明前提是「案例数据不随版本变，规则随版本变」。这个前提已被证否：

| 案例 | verdict 提交日 | `data/` 最后改动 | 判定 |
|---|---|---|---|
| 12/12 案 | 09-04 ~ 09-09 | 全部 09-11 | ⚠ 数据晚于 verdict |

- 09-11 的 schema 迁移 `f972e63` 给 43 份底稿统一注入 `meta` 块（`unit` / `currency` / `data_vintage` / `source_ref` …）；
- NFLX 底稿今日还有实质改动（`point_in_time_waiver` 登记）；
- 神华（601088）更极端：`git ls-tree <verdict commit> .../data/` 返回**空**——该案的整个 `data/` 目录是在 verdict 之后才入库的。旧引擎在 `--as-of` 下拿到的输入，与它当初实际读到的输入根本不是同一批文件。

**软链整个 `backtest/` 是有代价的取舍**：不软链就拿不到 `.gitignore` 排除的原始抓取（`data/filings/`、`data/raw/companyfacts*.json`），软链就意味着数据不随版本回退。当前实现选了后者，但没有把「复现的是规则、不是数据」写进快照或输出。

### 2.4 第二重变量：`--as-of` 跑的是旧版 runner，复现失败无法归因

`--as-of` 在 worktree 里执行**旧版** `run_backtest_assertions.py`（本次实测中 HEAD 版 runner 的输出表头没有「规则版本」列，即 P0-08 落地前的版本）。旧版 rerun 路径自身带有已知缺陷（脚本注释自陈：`scenarios.json` / `scenarios_*.json` 双命名曾使 `check_scenarios`/`reverse_dcf` 在 rerun 路径被静默跳过，GATE 码全部误判为不可复现）。因此「复现失败」里同时混着**数据变量**和**旧 runner 缺陷**两个噪声源，结论不可归因。

### 2.5 建议修法（按性价比排序）

1. **快照增 `case_data_digest`**：`sha256(sorted(case/data/**/*.json))` 写入 `rules_snapshot`。`--as-of` 复现前校验摘要，不一致就在输出里标 `data_drifted` 并**拒绝声称复现成功**。
2. **`--as-of` 只 pin 引擎脚本，runner 用当前版**：把「引擎」（`reverse_dcf` / `check_scenarios` / `compute_metrics*` / `forensic_screen`）从 worktree 读，`run_backtest_assertions.py` 用当前工作区的（现代 rerun 逻辑会正确调用旧引擎）。这样复现失败只可能来自规则或数据，不再来自 runner 自身版本。
3. **加 `--expect-reproduce`**：`engine_derived` 零漂移才退 0，非零即退 1，作为验收的机器断言。当前 `--as-of` 与普通重跑共用退出码，`exit 0` 既可能是「复现成功」也可能是「本来就没漂移」。
4. **存量案例按 AST-009 处理**：不猜填快照，而是在战绩表标注「历史批次：不可机器复现（无规则快照 + 数据已迁移）」——需求文档验收条款可改为「第四批起适用；存量案例标不可复现程度」。

### 2.6 交叉印证：同仓库的 astra 清单已预先拒绝这套验收

`story/REQUIREMENTS-astra-20260910.md` §9 衔接表：

> | REQ-P0-08：钉死 Git hash 即可复现原档位 | 补齐数据、规则、环境和模型运行信息 | 代码版本不足以保证智能体研究复现；AST-008、009 |

即本次实测发现的缺口，另一份清单在需求层就判过。建议在 fable 版验收条款里显式引用该裁决，避免两份清单再次互相矛盾。

## 3. 【P1】`rules_version` 的 drifted 判定恒为真，信号失去区分度

`run_backtest_assertions.py:371-375`：

```python
head = _git_head()                      # repo HEAD
if snap.get("skill_commit") == head:    # 相等才 current
```

时间线推演：

1. 提交规则改动 → HEAD = X；
2. 跑 `--snapshot-rules`，记 `skill_commit = X`；
3. 写入 `verdict.json`；
4. `git add <case>/verdict.json && git commit`（PROMPT Step 3 强制「落盘后立即单独提交」）→ **HEAD 变成 Y**。

此后 `X != Y` 恒成立，**每一条 batch≥4 的 verdict 从落盘那刻起就永久显示 drifted**，`--as-of` 提示也无差别地打到所有案例上。叠加第二个噪声：`skill_commit` 是 repo HEAD，任何 docs / memory / 案例数据提交都会触发「假漂移」。

**建议修法**（一行 git 命令即可精确判定，不引入新字段）：

```python
r = subprocess.run(["git", "diff", "--name-only", f"{snap['skill_commit']}..HEAD",
                    "--", "scripts/", "references/", "SKILL.md"],
                   capture_output=True, text=True, cwd=REPO)
# 仅当规则文件集真正有差异 → drifted；否则 current
```

好处：① 提交 verdict 本身（只动 `backtest/`）不再造成漂移；② 文档/记忆提交不再造成假漂移；③ `drifted` 与 PROMPT「drifted 须用 `--as-of` 对读」的纪律在数量上第一次对得上，而不是每案都触发。若想更稳，可在快照里另存 `rules_fingerprint`（规则文件集内容 sha256），彻底摆脱 commit 图。

## 4. 【P1】`dirty` 判据是整个工作区，与 Step 2 → Step 3 流程冲突

`prepare_case.py:365`：`dirty = bool(git status --porcelain)`——**全仓库**任何未提交文件都算。而 PROMPT 的流程是：Step 1 提交 `meta.json + data/` → Step 2 跑完整分析（产出报告 HTML、底稿、`forensic.json`、`workpapers/` 等一堆文件）→ Step 3 落 verdict。

于是 Step 3 时工作区几乎必然 dirty（本次审查时实测 `dirty=true`，未提交文件包括 11 个）。lint 又会拒绝 `dirty=true` 的 verdict，执行者只有两条路：

- 为落盘前把 Step 2 全部产物提交（合理，但需要额外的 commit 纪律，且 `git add -A` 一把梭会**把 verdict 混进脏提交**，直接破坏 Step 3「verdict 单独提交」这条隔离时序证据——那是 P0-05 的地基）；
- 或者绕过 lint。

**建议修法**：`dirty` 只统计规则文件集（`scripts/`、`references/`、`SKILL.md`），或增加 `--rules-only` 开关并把「`dirty` 的语义是规则脏、不是工作区脏」写进 PROMPT Step 3。

## 6. 建议补充（工程细节，均已实测）

1. **`--snapshot-rules` 是纯手工粘贴 JSON 到 `verdict.json`**，没有 `--write` / 自动注入，也没有 hook。建议 `prepare_case.py --sign-verdict <case_dir>` 一步完成「生成快照 + 写入 verdict + 跑 lint」，减少漏字段与缩进事故。
2. **`--as-of=HEAD` 等号写法直接失败**（实测：`error: unrecognized arguments: --as-of=HEAD`）。`run_backtest_assertions.py:708` 的 passthrough 过滤只剔除 `"--as-of"` 与裸值，等号形式会原样透传给不认识它的旧 runner。建议按 `startswith("--as-of")` 过滤或改用 `argparse` 的 `parse_known_args`。
3. **`--as-of` 不校验目标版本是否就是 verdict 记录的版本**：手输任意 hash 都能跑，容易做成「拿 A 版本复现 B 案例」的误用。建议支持 `--as-of auto`（读 `verdict.rules_snapshot.skill_commit`），并在显式传 hash 与快照不一致时打印提示。
4. **`--as-of` 下相对路径会穿过软链落到真实仓库**：`-o out.json` 落在 worktree（会被清理，无害），但 `--baseline backtest/xxx.json` 会解析到**真实** `backtest/`。建议在 worktree 模式下把 `--baseline` 强制为绝对路径或直接禁用。
5. **P0-08 的测试只验「跑了 + 清理了」**（`tests/run_tests.py:2395-2400`），不验「复现了」。要落实 §2.5 的第 3 条，这条断言是必需的——否则 `--as-of` 可以在完全不复现的情况下长期绿灯。
6. **测试套件在受限环境下会静默中断**：本次审查中 3/5 次沙箱内运行出现 `exit=1`，但日志既无 `[FAIL]` 明细也无收尾汇总（stdout 块缓冲丢失，最后一行停在 14.3 中间），仅放开沙箱后同一命令 exit 0 全绿；另有一次运行在 14.3 段报出 2 项 `[FAIL]`（P0-05 `contaminated` 判定），单进程复跑 3 次均全过。这与今日已记录的**已知脆弱点**叠加：`tests/run_tests.py` 用固定临时目录名 `_TMP_TEST_2020-12-31`，并发跑两份会互相踩踏出假失败。属环境/并发相关性、非确定性缺陷，但对一个以「机器可验闸门」为卖点的仓库，**红灯没有原因**本身就是 AST-010 警告的那类问题。建议：① 临时目录名带 pid/随机后缀，杜绝并发踩踏；② 测试套件行缓冲输出并把失败摘要单独落盘（或 `-u`），让 CI 里的红灯可定位。
