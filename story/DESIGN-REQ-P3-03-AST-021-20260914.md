## 1. 共同前提：两条必须共用一个数据结构

### 1.1 为什么不能分开做

两条需求是同一母问题的两面：**"我凭什么认为我知道的比市场多"**。

- 需求1 回答**分歧是什么、我为什么对**（定性，五字段）
- 需求2 回答**分歧有多大、差在第几个参数上**（定量，价格反解）

若分头实施，会造出两张独立的表：一张写"我的不同观点是利润率会修复"，一张写"隐含要求利润率 12% vs 我方 15%"。**两表的数字与结论没有任何机器连接，各自都可以是对的，合起来却是空的**——这正是仓库"单一事实源"纪律要防的漂移源（`MAINTENANCE.md` 第 1 节）。

### 1.2 定案

以 **`variant_perception` 结构块**为唯一事实源：

- 需求1 负责该块的**完整性**（五字段齐全 + 证据指针）
- 需求2 的反解结果**填入**该块中 `my_view` / `market_view` 两格的量化内容，并由 `key_differences` 数组做逐参数展开
- 两边共用同一组 `[E:]` 证据指针，不各写一套

副产品：现行 SKILL.md Phase 4.5 用的是"三问"表述，需求文档用的是"五字段"表述，两者并存本身就是漂移源。本次实施以五字段为准，SKILL.md 只保留一行指针对齐（受"只减不增"约束，不动正文）。

## 2. 共享 schema 定义

> 以下定义是**唯一事实源**，实施时同步写入 `scenarios.json` 的 schema 说明段（脚本头 docstring）与 tests 断言，**不另开 references 文档**（`references/` 余量仅 60 字节，见第 5 节）。

### 2.1 `variant_perception` 块（新增）

```json
"variant_perception": {
  "market_view": "现价隐含要求未来 10 年收入 CAGR 11.3%（reverse_dcf implied-requirements）；卖方一致预期 2027 收入增速 9.8% [E:consensus_XXX.json]",
  "my_view": "我方基准 6.5%：新开门店单店产出已连续 3 季同比转负 [E:business_drivers_XXX.json]",
  "why_market_wrong": "市场把 2024 年的提价周期当成常态；渠道库存数据显示实际动销已回落 [E:phase3_analysis.md]",
  "verification": "2026 年报分部收入增速 + 存货周转天数；连续两期低于 8% 即坐实我方判断 [E:financials_XXX.json]",
  "check_by": "2027-04-30"
}
```

字段级规则（**全部为实施时的校验依据**）：

| 字段 | 类型 | 必填 | 额外约束 |
|---|---|---|---|
| `market_view` | str | 是 | **必须含至少一个量化锚**（现价隐含 X% 或 consensus 数值）；纯定性描述不满足 |
| `my_view` | str | 是 | 非空即可；若 `key_differences` 存在，二者语义必须一致（见 4.3） |
| `why_market_wrong` | str | 是 | **必须含 `[E:]` 指针**（复用 `E_PTR` 正则） |
| `verification` | str | 是 | **必须含 `[E:]` 指针** |
| `check_by` | str | 是 | ISO 日期 `YYYY-MM-DD`，且晚于分析日 |

"缺"的判定口径（三处校验必须一致）：键不存在、`null`、空字符串、纯空白 —— 四种状态**一律视为缺**。
（REQ-P3-03 说"任一为空"，若只判 `None`，一个 `""` 就能绕过，与 AST-022 验收"未知字段显式标注，不以空白绕过关键要求"同构。）

### 2.2 `key_differences` 数组（新增，需求2 Step2 使用）

```json
"key_differences": [
  {
    "param": "稳态 OE 利润率",
    "implied_requirement": 0.121,
    "my_call": 0.155,
    "gap": 0.034,
    "value_impact_per_share": 8.6,
    "verify_condition": "毛利率连续两期 <38% [E:financials_XXX.json]"
  }
]
```

- 条数：**1~3 条**（AST-021 原文：选择 1～3 个关键差异）
- `gap` 必须等于 `my_call − implied_requirement`（脚本重算比对，容差 1e-6）
- `verify_condition` 必须含 `[E:]`
- 允许显式声明"未识别可支持的认知差"（见 4.4），此时该数组可为空数组 + 声明字段

## 3. 需求1 实施细则（REQ-P3-03）

### 3.1 cap 机制：复用既有范式，不新造

现状盘点：仓库已有**两个** cap 源，位置不同、语义不同。

| cap 源 | 位置 | 取值 | 触发方式 |
|---|---|---|---|
| `gate_cap` | `reverse_dcf.py:2663-2694` | `excluded` / `small_position_probe_only` / `normal_gates_apply` | 估值通道级（growth/sotp/dividend/distress 自动写入） |
| `value_trap.verdict_cap` | `check_scenarios.py` S8 | `小仓位试探` / `排除`（`TRAP_VERDICT_CAPS`） | 条件触发（MoS>50% 且收入连续萎缩） |

本次新增**第三个 cap 源**，归属于 `check_scenarios.py` 那一族（Phase 4.5 门禁层），形态完全对齐 S8：

- 触发条件：`variant_perception` 不完整
- cap 值：**`观察等价格`**
- 对应 ordinal：**2**（依 `alert_codes.py:398` `VERDICT_ORDINAL`：排除 0 / 拒绝 1 / 观察等价格 2 / 小仓位试探 3 / 核心买入 4）

**cap 合并规则（本次必须显式新增，否则第二个 cap 源落地即产生未定义行为）**：

```
final_ordinal = min(闸门判定 ordinal, Σ 各 cap ordinal)
```

即 **cap 取更严者**。理由：S8 的 cap 可为 `排除`(0)，本次 cap 为 `观察等价格`(2)，二者同时命中时若不定序就会依赖代码书写顺序。序数越小越严，取 min 是唯一无歧义的规则。

**语义边界（重要）**：cap 是**上限**，不是错误。报告仍可交付，只是档位被钉住——与 S8"强制降档"同义。需求原文写的就是"档位上限锁定为观察"，而非"禁止出报告"。

### 3.2 三处校验点

| # | 位置 | 校验内容 | 失败语义 |
|---|---|---|---|
| 1 | `check_scenarios.py` 新增 **S12 段** | 五字段完整性 + `[E:]` 指针 + `check_by` 格式 | 写入 `variant_perception.verdict_cap = 观察等价格` + 披露码；不阻断（见 3.3） |
| 2 | `run_backtest_assertions.py --lint-verdict`（现 L595） | 同款五字段校验（回测侧口径一致） | 与 S12 同语义；回测侧额外要求 `verdict_ordinal ≤ 2` 否则判 FAIL |
| 3 | `verify_report.py` | 报告 HTML 的档位与 cap 一致 | FAIL（防"机器锁观察、报告仍写核心买入"） |

第 3 处是**必要的第三道闸**：前两处只保证底稿正确，若不校验报告，一份底稿写着"cap=观察"而报告首屏写"核心买入"的文件仍可交付——这正是 `verify_report.py` 存在的理由（守"报告 = 底稿"）。

### 3.3 一个必须拍板的设计分叉

REQ-P3-03 的原文语义指向**(b)**，但两种实现都有真实风险，实施前必须选一个：

**(a) 硬拒绝**——缺字段 → `check_scenarios.py` 退出码 1，不许进 Phase 4.5。

- 优点：与"错误清零才进下一步"的既有纪律完全一致（`validate_data` / `check_market_snapshot` 都是这个模式）
- 缺点：与需求原文"档位上限锁定为观察"不符。且会把"答不出"变成**流程中断**，而需求本意是"答不出**也是合法结论**，只是只能给观察"——硬拒绝反而会诱导执行者为了过闸而凑字段，正是需要防的

**(b) 降档放行**——缺字段 → 自动写 `verdict_cap = 观察等价格`，报告可出、档位被钉。

- 优点：与需求原文一致；"答不出只配观察"是**体面的答案**而非失败（对齐 SKILL.md 核心纪律第 3 条"敢说不"）
- 缺点：存在"交付一份档位是观察的报告就算完工"的走形风险

**建议取 (b) 为默认 + 三条防走形约束**：

1. 强制披露码 `VARIANT_PERCEPTION_INCOMPLETE_CAP` 进 `codes`（须在 `alert_codes.py` 注册，遵守码注册表铁律）
2. 报告**首屏**必须显示"因变异认知不完整而降档"，不得只写附录（对齐 `verification_strength` 徽章的"与结论同屏"纪律）
3. `key_differences` 非空而 `variant_perception` 不完整时**报错**（不是降档）——两表打架属结构性错误，不是"答不出"

另保留 (a) 作为开关 `--strict-variant`，供回测批次按需启用。

> **待裁决点 ①**：是否采纳"(b) 默认 + 三条防走形"。

### 3.4 存量兼容

- 12 个回测案例 + 10 个实盘 `cases/*/decision-log.json` **一律不回溯**（与 P0-04/P0-08 的"基线不动"纪律一致）

  - 第一层"块存在才校验"（对齐 S10/S11 的既有风格）→ 保护存量底稿不因缺块而报错

- 只做第一层等于没做，实施时必须两层同时落

### 3.5 负向测试清单（优先于正向，`MAINTENANCE.md` 第 2 节）

## 4. 需求2 实施细则（AST-021）

### 4.1 Step 1：`reverse_dcf.py` 新增 `implied-requirements` 模式

**反解目标**：给定"其他所有假设"，求支撑当前价格所需的单一经营变量值。

CLI 设计：

| 参数 | 必填 | 说明 |
|---|---|---|
| `--market-cap` | 是 | 当前市值（口径同 `implied-growth`，建议百万） |
| `--solve` | 是 | 反解目标：`growth` / `margin` / `roiic` / `terminal_g` |
| `--fix` | 是 | 固定参数：`"margin=0.18,roiic=0.15,discount_rate=0.10"` |
| `--years` | 否 | 预测期，默认同全局常数 |
| `--industry` | 否 | 行业名，用于基率对照（见下） |
| `-o/--output` | 否 | 输出 JSON |

输出 schema：

```json
{
  "mode": "implied_requirements",
  "solved": "growth",
  "status": "solved",
  "implied_requirement": 0.113,
  "fixed_params": {"discount_rate": 0.10, "years": 10, "terminal_growth": 0.025, "margin": 0.18},
  "applicable_domain": {"growth": [-0.5, 0.6]},
  "roundtrip_check": {"input_market_cap": 50000, "recomputed_market_cap": 50003,
                      "deviation": 6.0e-05, "pass": true},
  "base_rate_position": {"percentile": 88, "verdict": "落在基率 80 分位以上"},
  "conditional_on": "基期 OE 与再投资口径；改变基期假设结果会显著变化"
}
```

**必须遵守的五条纪律**：

1. **唯一正向引擎**：反解必须调用现有 `dcf_value()` 做二分，**禁止另写一套正向公式**。否则 `roundtrip_check` 必然自洽，这个自检就失去意义（自证循环）。
2. **固定参数清单强制输出**：AST-021 验收明文"每个反解写清固定参数及适用域"。只输出一个数字 = 未完成。
3. **`no_solution` 分支**：适用域内无解时返回 `status: "no_solution"` + `no_solution_reason`，**不得返回最近似值或边界值**。适用域沿用 `dcf_value` 既有的 `terminal_g_cap` / `min_spread` 约束（`reverse_dcf.py:57-58`）。
4. **措辞铁律**：字段名与输出文案统一使用 `implied_requirement`（隐含**要求**），**禁止出现"市场预期""市场认为"字样**。可加测试断言锁死——这是 AST-021 的核心语义修正：反解出来的是"若价格理性则该值必须为 X"，不是"市场真的这么想"。
5. **`conditional_on` 必填**：隐含值强烈依赖基期假设（海控案实证：基期一变，隐含增速剧变）。该字段是防止把隐含要求当成独立事实的护栏。

**`base_rate_position` 的衔接价值**：把隐含要求直接对照 `references/base-rates.md` 的行业分位。这正是 `OBS-VAL-01` 第 4 条（"反向 DCF 隐含增速的基率镜像检验缺失"，现留档待 Meta/中石油双向校准）缺的**载体**——该条留档的原因就是"隐含增速落在基率哪一档无判读规则"，本模式落地后判读规则才有地方挂。实施本步时应在 observations 同步登记该衔接关系，但不提前写判读规则（仍等双向校准）。

### 4.2 Step 2：`key_differences` 生成与校验

- 结构见 2.2；条数 1~3
- `value_impact_per_share` 的算法：把 `my_call` 与 `implied_requirement` 分别代入 `forward-value` 正向估值，差额即为该参数分歧对每股价值的影响。**依赖 AST-014（价值桥与归属权益口径）**——若 AST-014 未落地，须在报告显式标注该换算沿用的是当前口径
- 校验（落在 `check_scenarios.py`）：数组存在时 `gap` 重算比对、`verify_condition` 含 `[E:]`、条数 ∈ [1,3]

### 4.3 与需求1 的对齐（防两张表打架）

三条机器可检的对齐规则：

1. `key_differences` 非空 ⇒ `variant_perception` 必须五字段完整
2. `key_differences[i].my_call` 与 `variant_perception.my_view` 语义一致（机器只能检"同源引用"：要求两者引用同一 `[E:]` 文件，语义一致性留给红队人工核验并在报告披露核验范围——**不得假称正则能验证语义**，对齐 AST-029 的既有立场）
3. `key_differences[i].param` 若与 Phase 4.5 `key_variables[].name` 指向同一经营变量，必须用同一措辞（建一个最小词表，不自动模糊匹配）

### 4.4 无认知差分支

AST-021 验收明文：**没有可靠分歧证据时输出"未识别可支持的认知差"，不编造市场观点。**

实现：`key_differences` 为空数组 + `no_variant_identified: true` + 理由字段。此时需求1 的 `variant_perception` 允许仅填 `market_view`，其余四格填显式的"未识别"，**但仍触发 cap**（识别不到认知差 ⇒ 只能给观察）——两条需求在此处自然咬合，不需要额外规则。

### 4.5 验收（照需求原文）

每个反解写清固定参数及适用域；价格代回正向模型一致（`roundtrip_check.pass = true`）；无解明确报告；没有可靠分歧证据时输出"未识别可支持的认知差"。

### 4.6 依赖与口径风险

| 依赖 | 影响 | 处理 |
|---|---|---|
| AST-014 价值桥 | `value_impact_per_share` 的口径正确性 | Step1 不依赖，可先做；Step2 的该字段要么等 AST-014，要么显式标口径 |
| AST-013 经营→现金流链 | `--solve roiic` 的再投资口径 | `growth` / `margin` 两个目标不依赖，可先做 |
| AST-017 情景概率 | `--solve terminal_g` 的适用域 | 可后置 |

→ **Step1 建议只先做 `growth` 与 `margin` 两个反解目标**，`roiic` / `terminal_g` 等上游就绪后再加。这符合仓库"≥2 案例才改码"的最低成本路径。

## 5. 落地顺序与前置约束

### 5.1 顺序

```
第 1 步  需求1（REQ-P3-03）        — 无依赖、成本小、直接减少"假买入"结论
第 2 步  需求2 Step1（growth/margin 反解）— 是 Step2 的地基，且是 OBS-VAL-01④ 的载体

```

### 5.2 三条硬约束（动手前必须知道）

1. **`references/` 体积余量仅 60 字节**（153,540 / 153,600），是机器红线（`tests/run_tests.py` 检查）。新增细则文档前必须先压缩等量。→ 本方案的落点是 `scenarios.json` schema 说明段 + 脚本头 docstring + 本设计文件，**不新开 references 文档**。`SKILL.md` 余量约 4.2KB（41,899 / 46,080），但也受"只减不增"，只允许加指针行。
2. **改 `scripts/` 前后各跑一次 `tests/run_tests.py`**（当前基线 777 项全 PASS）。负向用例优先。
3. **新增闸门必须做判别力检验**（`MAINTENANCE.md` 第 3 节）：cap 加第三级后，把已有案例全部重算一遍看档位分布。若结果**过度集中于"观察"**（如多数案例被 cap 拉下来），说明字段门槛过严或口径有系统性偏差——先怀疑设计，不要断言"这批公司就是答不出"。
